# v0.5 分支 trace 与 BTB 可行性分析

> 结论：**BTB 值得做，但只能做小的**。16 项直接映射 + 8 项返回栈就能拿到
> 91.8% 的 redirect 消除率，理论 CPI 1.256 → 1.143、CoreMark 37.2 → 40.9；
> 代价是取指路径要多一级查表，**Fmax 一旦低于 91 MHz 就是净亏**。

## 1. 方法

- `sim/tb_v4_trace.v`：跑完整顶层（ROM/RAM/UART/计数器），在 IF/ID 的下降沿
  把每条执行过的条件分支 / JAL / JALR 记录成
  `cycle pc type taken target rd rs1`。
- 固件：CoreMark `-DITERATIONS=1`（`build_sw.py --iterations 1`），
  仿真 8M 周期，去掉 `main()` 返回后 `j .` 的空转段后，有效部分 6.79M 周期，
  约 2.5 次迭代。
- 自洽性校验：记录的 1,855,718 条与 `retire_cls==3` 的退休计数 1,855,717
  完全一致，说明 trace 没有漏记/重复。

## 2. trace 画像

```
cond  1,192,559   taken 85.5%
jal      29,945
jalr     27,081
redirects 1,077,073  (== 当前设计每次 1 拍的 flush 来源)
```

稳态（每 1M 周期窗口）里几乎不出现"预测 taken 但实际 not taken"，
启动/初始化阶段的误报明显更多（窗口 0～2 的 lose 是 27K～43K，
窗口 3～5 只有约 250）。

> 口径提示：板上 PERF 计数给出 `br taken 125.6M / br not 99.9M`（taken 55.7%），
> 与本 trace 的 85.5% 不一致；仿真内部记录数与退休数严格相等，因此
> 本文按 trace 计算，并在第 4 节给出把误报放大 10 倍的敏感性结果。

## 3. 配置扫描

模型：取指时查表，命中且 2-bit 计数器 ≥2 则预测 taken；EX 验证方向与目标。
基线（静态 not-taken）每次 redirect 1 拍。

| 配置 | save | lose | net | 占 redirect | 投影 CPI | 投影 CoreMark | 盈亏平衡 Fmax |
|---|---|---|---|---|---|---|---|
| BTB 16 1w 2bit | 1,031,822 | 50,582 | 981,240 | 91.1% | 1.144 | 40.83 | 91.1 MHz |
| BTB 32 1w 2bit | 1,063,336 | 89,698 | 973,638 | 90.4% | 1.145 | 40.80 | 91.2 MHz |
| BTB 64 1w 2bit | 1,071,916 | 98,634 | 973,282 | 90.4% | 1.145 | 40.80 | 91.2 MHz |
| BTB 128 1w 2bit | 1,072,699 | 100,207 | 972,492 | 90.3% | 1.145 | 40.80 | 91.2 MHz |
| BTB 256 1w 2bit | 1,075,019 | 107,206 | 967,813 | 89.9% | 1.146 | 40.78 | 91.2 MHz |
| RAS8 only | 13,520 | 0 | 13,520 | 1.3% | 1.254 | 37.25 | 99.9 MHz |
| **BTB 16 + RAS8** | 1,044,568 | 56,320 | **988,248** | **91.8%** | **1.143** | **40.86** | **91.0 MHz** |

几个要点：

1. **16 项就到顶了**。再大只会增加误报（lose 从 50K 涨到 107K），净收益反而下降：
   CoreMark 的热点分支只有十几个，容量不是瓶颈，预测器保守程度才是。
2. **RAS 单用没有意义**（jalr 只占 2.5%），但和 BTB 合用能多拿 0.7%：
   `jalr` 的 `wrong_tgt` 从 1,412 降到 5。
3. **2 路/4 路更差**：组相联把索引位减少，热点分支冲突反而变多（16 项 2 路只有 76%）。
   直接映射 1 路是正确选择。
4. **收益几乎全是条件分支**：save 里 996K 来自 cond，jal/jalr 合计只有 48K。

## 4. 敏感性

板上 PERF 给出的 not-taken 比例更高（44% vs trace 15%）。把 lose 整体放大 10 倍：

```
net = 1,031,822 - 505,820 = 526,002  ->  48.8% of redirects
CPI  = 1.19   CoreMark = 39.4   f_min = 94.5 MHz
```

即使这样，收益仍有 **+6%**，只是盈亏平衡点抬到 95 MHz。
所以"做不做"的答案不取决于 trace 口径，而取决于 pc 路径能不能在 10 ns 内
多塞进一级查表。

## 5. 如果要做，建议的形态

```
IF:   pc ──► BTB 索引/读 ──► hit && ctr>=2 ? target : pc+4 ──► pc'
      BTB: 16 项直接映射，每项 {tag, target, 2-bit ctr}
      RAS: 8 项，JAL/JALR with rd∈{x1,x5} push pc+4，jalr with rd=x0 pop
EX:   验证方向 + 目标；不符则 flush，并写回 BTB（taken 时更新 target，ctr±1）
```

资源估算：16 项 × (tag 20b + target 32b + ctr 2b) ≈ 864 bit，用 LUTRAM 约
16 个 LUT6（每 LUT 64×1）+ 一个 20 位比较器，合计 ~40 LUT；RAS 8×32 位 ~16 LUT。
相对当前 2339 LUT 可以忽略。

风险全在时序：`pc → BTB 读 → mux → pc'` 是新的一条组合路径，而当前
WNS 只有 +0.036 ns（关键路径是 ROM→ALU，不是 pc）。如果 Vivado 把 BTB 的
LUTRAM 放在 pc 附近，这条路径约 3～4 ns，应该塞得下；但 `redirect` 的
修正 mux 会叠在同一个 pc 端点上，需要实测。

## 6. 复现

```bash
python scripts/build_sw.py --mode coremark --iterations 1 \
       --build-dir sw/build_trace --rom-out rtl/myxtrv32_rom_sim.v

iverilog -g2012 -o sim/iv/f_trace.vvp -s tb_v4_trace \
    rtl/myxtrv32_core_v4p.v rtl/myxtrv32_top_v4.v rtl/myxtrv32_ram.v \
    rtl/myxtrv32_uart_tx.v rtl/myxtrv32_rom_sim.v sim/tb_v4_trace.v
vvp sim/iv/f_trace.vvp            # 约 145 s，写 out/branch_trace.txt

python scripts/btb_analyze.py out/branch_trace.txt
```
