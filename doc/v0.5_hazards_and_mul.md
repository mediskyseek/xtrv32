# v0.5 —— 冒险修复 + MUL 单拍，实测记录

> 结论先行：**两条被指出的冒险都是真问题，但只有一条影响性能，另一条是正确性**。
> MUL 从 2 拍压到 1 拍可行，且没有吃掉时序余量。
> 真正让 v0.5 的 WNS 回正的，不是 MUL，而是分支前递源改成 `mem_wb_alu`。

## 1. 版本澄清

| 位置 | 实际内容 |
|---|---|
| `rtl/myxtrv32_core_v4p.v` | **唯一在用的实现**，四级流水线，`build.tcl` 在 top=`myxtrv32_top_v4` 时编译它 |
| `rtl/myxtrv32_core_v4.v` | 早期**三级骨架**，只实现 LUI/AUIPC/OP-IMM/OP（无 M/LOAD/STORE/BRANCH），没有被任何脚本引用 |
| `README.md` | 正文仍停在 v0.3（多周期 FSM），未随 v0.4/v0.5 更新 |

所以"公开仓库与 v0.4 不一致"成立，但原因不是"公开的是三级完整实现"，
而是 `core_v4.v` 是没人用的骨架、README 没更新。

## 2. 两个冒险：一个性能，一个正确性

### 2.1 load-use 只看 [24:20]（性能，收益极小）

`stall_load_use` 与 `br_load_dep` 原来直接比较 `rs1/rs2` 字段，而 OP-IMM / LOAD /
JALR 的 [24:20] 是立即数位。修复后加 `uses_rs1/uses_rs2`。

**实测代价**（CoreMark 600 iterations）：

```
load-use stall cycles: 45,841,122 -> 45,832,122      ( -9,000 )
总周期             : 1,688,845,209 -> 1,688,836,209  ( -0.0005% )
CPI                : 1.31499 -> 1.31499
```

即：假停顿在真实代码里只占 load-use 停顿的 0.02%。**这项改动几乎不产生性能**，
只作为顺手的正确性整理保留。

### 2.2 MUL/DIV 启动不看 load-use（正确性，会算错）

`mul_start` 只要求 `!stall_d`，因此在 `lw` 的 load-use 冒泡周期里，
MUL 会从 EX/MEM 前递拿到 **load 的地址**并锁存。

定向测试 `sw/hazard_test.S`（修复前）：

```
lw  x1, 0(x2)      # x1 = 0x1234，地址 0x0001_0000
mul x4, x1, x5     # 期望 0x369C，实测 0x0003_0000 = 地址 × 3
div x9, x8, x5     # 期望 25，  实测 0x5556     = 地址 / 3
```

修复时踩到的第二个坑：最初把保护写成 `mul_start && !stall_load_use`，
但 `mul_start` 同时带 `!stall_d`，而 load-use 冒泡之后的下一拍 `stall_d = 1`，
于是 MUL **永不启动**，直接以陈旧的 `mul_full_r` 退休（`x4 = 0`）。
正确做法是记住"上一拍是不是 MUL/DIV 自己造成的停顿"（`stall_md_q`），
而不是复用 `stall_d`。

代价：`LW -> MUL/DIV` 由 2 拍变 3 拍（必须等 load 数据到 WB），
普通 MUL 不受影响。

### 2.3 顺带修掉的：flush 后的 MUL

`mul_start` 没有 `if_id_valid`，被冲刷的错误路径 MUL 仍会启动并让前端白停 2 拍。
现在不会了。

## 3. MUL 单拍：可行

`mul_full_w[31:0]` 直接送 EX/MEM（`f3 == 3'b000`），`MULH/MULHSU/MULHU`
仍走寄存后的 64 位乘积。

**实测**（板上 100 MHz，600 iterations，CRC 全对）：

| 项目 | v0.4 | v0.5 | 变化 |
|---|---|---|---|
| cycles | 1,688,845,209 | 1,612,696,209 | **−76,149,000 (−4.5%)** |
| instret | 1,284,402,099 | 1,284,402,099 | 0 |
| CPI | 1.315 | **1.256** | −0.059 |
| `stall md` | 152,280,000 | 76,140,000 | **正好减半** |
| CoreMark 1.0 | 35.53 | **37.20** | +4.7% |
| WNS (release) | +0.044 | +0.036 | −0.008 |
| WNS (perf) | −0.225 | −0.217 | +0.008 |
| LUT | 2294 | 2339 | +45 |
| FF | 633 | 661 | +28 |

关键点：**MUL 快通道本身没有成为关键路径**。`v0.3` 文档里"DSP 合并回一拍
WNS −3.612"的结论在这里不成立，因为只取低 32 位、且操作数已寄存，
Vivado 把 32×32 映射到 4 个 DSP48E1 后组合延迟仍在 10 ns 内。

## 4. 真正吃掉时序的是什么

加入冒险逻辑后 WNS 从 +0.044 掉到 **−0.315**，最差路径变成
`ROM -> rs2 -> fwd_wb_br_b -> 分支比较 -> pc`（15 级）。

两次尝试：

| 改动 | WNS |
|---|---|
| 原始 v0.4 | +0.044 |
| +uses_rs1/rs2 +mul 保护（lu_raw 进 stall） | −0.315 |
| lu_raw 从 stall 摘出，只挡 capture / stall_md_q | −0.159 |
| 合并 hit1/hit2 比较器 | −0.170 |
| 删除重复的 mul_a_r/mul_b_r | −0.226 |
| `place_design -directive ExtraTimingOpt` | −0.047 |
| **分支前递源 wb_data -> mem_wb_alu** | **+0.036** |

最后一项才是决定性的：`fwd_wb_br_*` 已经排除了 load，所以 `mem_wb_alu`
与 `wb_data` 在同一条件下等值，但前者把 RAM 输出彻底移出分支比较锥。

## 5. 下一步的判断

- **分支冲刷（+0.123 CPI）**：静态不跳转 + EX 级解析，每次 redirect 固定 1 拍。
  要吃这块必须做 BTB（取指级给目标），BHT 单独无效。风险是 pc 路径再加一级 mux，
  而当前余量只有 0.036 ns。
- **分支依赖 load（+0.038）**：已经是"停 1 拍"的最优解（不绕 RAM），
  除非把分支比较挪到 MEM 级加息，否则没有空间。
- **普通 load-use（+0.036）**：同理，1 拍即下限。
- **DIV**：CoreMark 里 div=0，无需投入。
